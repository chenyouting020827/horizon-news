## [Rust 1.100 Stabilizes Never Type, Custom Allocators and Cargo Dependency Cooldowns](https://blog.rust-lang.org/2026/11/12/Rust-1.100.0/) ⭐️ 8.0/10

Rust 1.100.0 was released on November 12, 2026, stabilizing the never type `!`, the core of the `allocator_api` (the `Allocator` trait, usable with `Vec` and `Box`), and a set of Cargo improvements: dependency cooldowns via a minimum publish age (RFC 3923), unused-dependency warnings, and `cargo install` now honoring the lockfile in the .crate tarball by default so `--locked` becomes a no-op. The release also ships `DropGuard` and several stabilized APIs that did not even make the blog post, such as `bool::toggle()`, `Box::map()`, and `str::trim_prefix()`/`trim_suffix()`. The never type and custom allocators are two of the longest-awaited stabilizations in Rust's history, giving library authors a way to plug in their own memory allocation strategies and letting type inference finally treat diverging expressions (like `panic!` or `exit`) coherently. The Cargo changes affect every Rust developer in daily work, since unused-dependency warnings and dependency cooldowns directly improve supply-chain hygiene and build correctness for the whole crates.io ecosystem. Custom allocators are only partially stabilized: the `Allocator` trait currently works with `Vec` and `Box`, while non-ZST allocator support remains behind a feature gate (tracking issue #163738). With dependency cooldowns enabled, the resolver ignores crate versions published more recently than the configured minimum age unless they are already pinned in `Cargo.lock`, and unused-dependency reporting defaults to `warn` through the `cargo::unused_dependencies` setting.

hackernews · mbStavola · Nov 12, 18:39 · [Discussion](https://news.ycombinator.com/item?id=50472038)

**Background**: Rust follows a six-week release cadence, so version numbers climb quickly and each release bundles whatever features cleared stabilization review. The never type `!` denotes computations that never produce a value — such as `panic!`, `std::process::exit`, or an infinite loop — and it can be coerced into any other type, making it essential for generic code and control-flow typing. `allocator_api` is a long-running unstable feature that lets code choose how memory is allocated rather than always relying on the global allocator, which matters for embedded systems, game engines, and other performance- or memory-sensitive domains. Cargo is Rust's build tool and package manager, and it resolves dependency versions from crates.io according to semver requirements declared in `Cargo.toml`.

## [Essay argues math alone cannot make software correct](https://pron.github.io/posts/correctness-and-complexity) ⭐️ 7.0/10

A 2016 essay by the author behind pron.github.io, "Why writing correct software is hard and why math (alone) won't help us," resurfaced on Hacker News and drew 343 points and 164 comments. Its central claim is that mathematical formalization can describe software precisely but cannot by itself resolve correctness problems in large, complex real-world systems. The debate strikes at a long-running split in computer science between formal verification and empirical, testing-driven engineering, and it matters to anyone deciding how much rigor is worth paying for in a codebase. It also frames why verified kernels and compilers remain rare exceptions while most production software still ships with bugs. The essay leans on complexity and undecidability arguments, including Rice's theorem, to show that general-purpose correctness checking cannot be automated, and it stresses that a proof is only as meaningful as the specification it is checked against. The argument is about limits, not dismissal: formal methods still pay off in narrow, well-specified domains such as compilers, cryptographic primitives, and protocol state machines.

hackernews · AriFordsham · Nov 12, 10:28 · [Discussion](https://news.ycombinator.com/item?id=50465352)

**Background**: Formal methods are techniques that model software as a mathematical object so properties can be proved rather than merely tested; Hoare logic, for example, treats programs as predicates over states. A specification is the precise statement of what a program is supposed to do, and every proof is relative to it — a verified program can still be wrong if the specification is wrong. Rice's theorem states that no general algorithm can decide nontrivial semantic properties of arbitrary programs, which sets a hard ceiling on fully automated verification. In practice most correctness work is empirical: testing, fuzzing, code review, and monitoring in production.
